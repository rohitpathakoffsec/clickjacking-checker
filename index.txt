This finding is a retest of #PT-DTT-0213#VA11. Considering the presence of multiple reflected XSS scenarios within the SSO ecosystem, the rating has been increased from Informational to Minor according to CVSS calculation.
Scenario 1 – Direct Reflected XSS in ISSO
The ISSO application was found vulnerable to reflected Cross-Site Scripting (XSS) through the Referer and User-Agent HTTP headers. Reflected XSS occurs when an application includes user supplied input within the server response without applying appropriate sanitization or output encoding.
During testing, malicious JavaScript payloads injected into HTTP headers were reflected within the application response inside executable JavaScript context, resulting in successful client-side script execution.
The identified issue requires an authenticated user session and successful delivery of a crafted request to the victim user. No straightforward unauthenticated exploitation scenario was identified during testing; however, successful exploitation may still be possible through crafted requests and user interaction.

Scenario 2 – Reflected XSS via SwisKey POST Preservation Mechanism During SSO Flow
A separate reflected XSS scenario was identified involving the SwisKey application and the SSO POST preservation workflow.
During testing it was observed that the SwisKey application processes user supplied input within HTTP POST parameters without sufficient validation or sanitization. The entire POST body is preserved using the SMPostPreserve mechanism during the SSO authentication workflow.
In this process:
User supplied POST data is encoded
Transported through the SSO workflow
Decoded by downstream components
Reused without sufficient sanitization after decoding
As a result, malicious input originating from SwisKey parameters may propagate through the SSO workflow and ultimately execute within the user’s browser when rendered by downstream ISSO-related components.
It should be noted that direct usage of the SMPostPreserve parameter was not observed within standalone ISSO requests during testing. Therefore, exploitation of this scenario requires an upstream application leveraging the POST preservation mechanism (such as SwisKey) rather than direct interaction with ISSO alone.
The response includes user controlled input that is reflected back to the client without sufficient sanitization, allowing attackers to inject arbitrary JavaScript or HTML content into the victim’s browser session.
